# Resource budget

## Configured starting limits

The generated user systemd unit sets Nice=10, CPUWeight=20, CPUQuota=20%, MemoryHigh=128M, MemoryMax=192M, TasksMax=32, and requests IOWeight=20. On this host the user service cgroup exposes only cpu, memory, and pids controllers, so IOWeight is not enforced without changing system-wide delegation. The unit also uses NoNewPrivileges, PrivateTmp, ProtectSystem=strict, read-only home protection, kernel-tunables and control-group protection, with write paths limited to Sentinel config/data. ProtectKernelModules is omitted because this host's unprivileged user manager cannot enforce it (a transient unit probe exits with 218/CAPABILITIES). These are guardrails, not measurements of actual idle use.

## Collection work

Host metrics default to 5 seconds; process inventory 10 seconds; sensors/GPU 15 seconds; service listing 60 seconds. Process/service operations are bounded. nvidia-smi has a 3-second timeout and kill-on-drop; service listing has a 3-second timeout per scope. The notification queue holds at most 16 jobs, deliveries time out after 5 seconds and may retry three times. AI has a 5–180-second timeout, loopback-only destination and host-pressure gate.

When available memory falls below 10%, CPU PSI exceeds 50%, memory PSI exceeds 20%, or reported CPU temperature reaches 95% of its limit, detailed process polling slows to three times its configured interval (capped at 300 seconds), baseline training pauses, and hourly database cleanup is deferred. Host metric sampling continues. Only one AI investigation may run at once; AI uses stricter guards and is refused at its investigation endpoint when pressure is high.

## Storage

Defaults retain raw host/process observations for 48 hours, process lifecycle events for up to seven days, minute points and anomalies for 30 days, and quarter-hour points, notification history, and recovered incidents for 365 days. SQLite budget defaults to 500 MiB and includes WAL sidecars. Under budget pressure cleanup trims older lifecycle events first, then process detail, raw metrics, and older aggregates; incident history remains separate. Monitor database and free disk because file size can remain elevated until checkpoint/vacuum.

On 2026-11-24 after the final release build, `/` was 501,864,161,280 bytes total, with 462,708,748,288 used and 13,586,886,656 free (12.66 GiB; 98% by `df`). Inode use was 3,451,674 of 31,195,136 (12%). The project, binary, config, service unit, and database paths all resolve to the same root filesystem. Visible `du -x` consumers included `/home` (~230 GiB), `/srv` (~42 GiB), `/tmp` (~29 GiB), `/var/log` (~12.8 GiB), `/var/lib` (~11.3 GiB), and `/usr` (~21 GiB). Unprivileged visible traversal accounted for about 352 GiB against about 431 GiB used; the remaining ~79 GiB was not attributed. A read-only root-level `du` attempt could not run because `sudo -n` requires a password, so the hidden/unreadable allocation remains unresolved. No unrelated files, data, backups, databases, or caches were deleted. A 50-second check before compilation changed free space by about 0.4 MiB; during the earlier four-minute service observation it changed by about 1.3 MiB while the Sentinel database grew about 0.49 MiB. Those short windows do not establish a long-term filesystem trend. The additional debug and release build artifacts were retained; no cleanup was performed.

## Measurement status

The 2026-11-24 controlled observation used five samples one minute apart over four minutes, with no synthetic load on the host. The service averaged about 0.84% of one core across that window (including light API/SSE probes), with current RSS around 14.9 MiB and process RSS high-water mark 32.9 MiB. Its cgroup memory current was about 12.1 MiB, with a 30.9 MiB peak, and it used three tasks. The database grew from 11,133,416 to 11,641,320 bytes (~0.49 MiB). Host process count ranged from 465 to 476. Sampled core temperatures were 56–61°C; memory PSI was 0%, CPU PSI 0.19–0.91%, and I/O PSI 0.93–1.26%. Available RAM was about 4.9 GiB. Swap was fully occupied, but `vmstat` showed zero swap-in/out in the two interval rows after its initial since-boot row. The service remained healthy, collector errors were absent, and it stopped with no remaining listener before restarting cleanly. This is a short operational check, not a multi-day stability claim.

After the final build was installed, a 6m28s runtime sample including authenticated API/SSE checks showed 3.36 seconds cumulative service CPU (~0.87% of one core), 14.1 MiB RSS, 12.2 MiB cgroup memory current, 27.7 MiB cgroup peak, and three tasks. The active user service has `Nice=10`, `CPUWeight=20`, `CPUQuota=20%`, `MemoryHigh=128M`, `MemoryMax=192M`, `TasksMax=32`, and `IOWeight=20`. The user service cgroup exposes CPU, memory, and PID controllers only, so IOWeight is configured but not enforced. `ProtectKernelModules` is omitted because the unprivileged user manager rejected it with `218/CAPABILITIES`; other configured sandbox limits were verified on the active unit. The user manager already had lingering enabled; Sentinel did not change it. The unit is enabled under `default.target`; boot startup was not reboot-tested.
